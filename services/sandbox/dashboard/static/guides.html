Sandbox Kit — Hướng dẫn sử dụng

Sandbox Kit là hạ tầng thực thi từ xa cho AI agent: một Relay Broker (FastAPI, cổng 8000) nhận lệnh HTTP từ orchestrator/subagent, chuyển tiếp qua WebSocket tới Go Runner chạy bên trong Docker sandbox, kèm VFS Service (SQLite, cổng 8001) làm nguồn sự thật cho file dự án.

Agent không bao giờ chạy code trực tiếp trên máy chủ — mọi lệnh shell, thao tác file đều diễn ra bên trong container cách ly, kết quả trả về qua Broker. Điều này cho phép orchestrator điều phối nhiều sandbox song song (mỗi pipeline một session) mà không đụng vào môi trường host.

Requirements

  • Server có Docker + 2 systemd service: sandbox-broker (cổng 8000) và sandbox-vfs (cổng 8001, chỉ nội bộ)
  • Container image cần chạy test phải có sẵn trên server — pre-pull trước khi tạo session (lần pull đầu sẽ block tạm Broker)
  • Client chỉ cần truy cập được cổng 8000; VFS 8001 do Broker tự proxy
  • Sandbox image chứa Go runner tĩnh (/opt/container_runner) — được provisioner mount tự động

Không có authentication

Các endpoint management / agent / VFS hiện chưa có auth. Chỉ triển khai trong mạng nội bộ, không mở cổng ra Internet công khai.

How It Works

  1. Orchestrator tạo session qua POST /api/v1/management/sessions — provisioner docker run container với Go runner được mount, inject BROKER_HOST/BROKER_PORT qua host.docker.internal:host-gateway.
  2. Runner trong container kết nối WebSocket về /ws, đăng ký role executor → session chuyển sang READY (runnerConnected: true).
  3. Subagent gửi action (runShellCommand, runReadFile…) tới POST /api/v1/agent/execute → Broker relay qua WS kèm requestId, chờ actionResponse.
  4. Trước mỗi lệnh shell, Broker tính VFS delta và đẩy sync_files vào container — VFS là nguồn sự thật, container là nơi thực thi.
  5. Kết quả trả về dạng chuẩn: status, stdout, stderr, exitCode, durationMs.

Vòng đời session

lifecycle
sandbox_create ──▶ STARTING ──▶ READY (runner connected) ──▶ làm việc ──▶ sandbox_terminate
                                          │
                            tạo với standby=true ──▶ STANDBY ──▶ sandbox_attach ──▶ READY

TTL hết hạn (mặc định 3600s) → TTL Reaper dọn container; ttl=0 → không bao giờ hết hạn

ttl = 0 nghĩa là bất tử

Session ttl=0 (mẫu dùng cho pipeline reuse) sẽ không bao giờ bị Reaper dọn. Nếu teardown DELETE thất bại, container 2vCPU/4Gi sẽ rò rỉ trên server. Luôn có cơ chế teardown rõ ràng trong pipeline.

Quick Start

1. Tạo session

bash
curl -X POST "http://localhost:8000/api/v1/management/sessions" \
  -H "Content-Type: application/json" \
  -d '{
    "project_path": "my-project",
    "image": "ubuntu:latest",
    "cpu": "2",
    "memory": "4Gi",
    "ttl": 3600
  }'

# → { "sessionId": "sess-abc123", "sandboxId": "sbx-...", "status": "success" }

project_path là định danh project workspace — đồng thời là tên workspace trên VFS. Nếu giá trị trùng đường dẫn host tồn tại trên server, volume /workspace được seed từ đó.

2. Chờ runner kết nối

bash
curl "http://localhost:8000/api/v1/agent/sessions/sess-abc123/status"
# → { "status": "READY", "runnerConnected": true, ... }

3. Thực thi lệnh trong container

bash
curl -X POST "http://localhost:8000/api/v1/agent/execute" \
  -H "Content-Type: application/json" \
  -d '{
    "session_id": "sess-abc123",
    "action": { "runShellCommand": { "command": "echo hello && uname -a", "timeout": 120 } }
  }'

4. Hủy session

bash
curl -X DELETE "http://localhost:8000/api/v1/management/sessions/sess-abc123"

Executing Actions

Một request /execute chứa đúng 1 action. Tất cả response dùng cấu trúc chuẩn với requestId duy nhất.

runShellCommand

json
{
  "session_id": "sess-abc123",
  "action": { "runShellCommand": { "command": "npm test", "timeout": 120 } }
}

Lệnh chạy bằng /bin/sh -c với cwd /workspace bên trong container. Broker chờ tối đa 300s (quá hạn → status: "timeout", exitCode: null).

Invariant: status = "success" ⇔ exitCode == 0

Lệnh shell thoát ≠ 0 luôn trả status: "error" kèm exitCode + output trung thực. Consumer phải kết luận pass/fail theo exitCode, không theo status. Process nền bắt buộc redirect pipe (nohup ... > /tmp/aut.log 2>&1 &) — nếu process giữ pipe, lệnh sẽ block mãi.

runReadFile / runWriteFile / runEditFile

json
{
  "session_id": "sess-abc123",
  "action": { "runReadFile": { "filepath": "src/app.js" } }
}

Đường dẫn là workspace-relative (src/app.js → /workspace/src/app.js). Broker chấp nhận path absolute /workspace/... và tự chuẩn hóa. File project đi qua VFS (SQLite, có revision history); đường dẫn dưới /tmp/* và /scratch/* là scratch — bỏ qua VFS, chỉ tồn tại trong RAM container.

VFS & File Sync

VFS là nguồn sự thật cho file dự án. Mỗi lần chạy runShellCommand, Broker tính delta giữa trạng thái VFS và lần sync trước, gửi khối sync_files (base64) vào container trước khi thực thi:

json — WS message (Broker → Runner)
{
  "requestId": "3f4a91bc-...",
  "runShellCommand": { "command": "npm test", "timeout": 120 },
  "sync_files": {
    "changed": [ { "path": "src/app.js", "contentBase64": "Y29uc29sZS5sb2coJ2hlbGxvJyk7" } ],
    "deleted": [ "src/old.js" ]
  }
}
  • sync_files chỉ xuất hiện khi session được provision với project_path ≠ /workspace và có delta
  • VFS endpoint: GET/POST /api/v1/vfs/file/{read,write,edit} với workspace_id = tên project workspace (Monarch connector tự resolve qua endpoint /workspace)
  • Workspace mới được VFS tự tạo khi ghi lần đầu; mọi ghi đè tự tạo revision snapshot

Binary artifacts

File do test sinh ra trong container (screenshot, trace.zip) nên đọc bằng runShellCommand "base64 -w0 <file>" rồi decode phía client, hoặc đợi action exportFiles (batch tar) trong roadmap.

WebSocket Protocol

Runner kết nối tới ws://<broker>/ws và duy trì vòng đời:

1. register (Runner → Broker)
{
  "type": "register",
  "role": "executor",
  "sessionId": "sess-abc123",
  "runnerId": "runner-sbx-...",
  "status": "READY",
  "workspace": "/workspace"
}
// Broker ack: { "type": "registered", "sessionId": "sess-abc123" }
2. actionResponse (Runner → Broker)
{
  "actionResponse": {
    "requestId": "3f4a91bc-...",
    "execution": { "status": "success", "stdout": "...", "exitCode": 0, "durationMs": 4821 }
  }
}
  • Keepalive: Broker gửi text ping, runner trả pong
  • Runner mất kết nối → session về STANDBY (container vẫn sống), gắn lại bằng POST .../attach-runner
  • Broker chấp nhận cả casing requestId (canonical) và requestID (legacy binary) khi nhận response

Best Practices & Gotchas

  • Runtime nằm trong image, không phải plugin — cần Playwright/Node/Python? dùng image tương ứng khi tạo session, điều khiển qua bash
  • Pre-pull image trên server trước khi tạo session với image mới (docker pull ...) — lần pull đầu sẽ block tạm Broker
  • Process nền redirect pipe — nohup cmd > log 2>&1 &, nếu không lệnh shell sẽ block tới timeout
  • TTL — mặc định 3600s; ttl=0 = bất tử; pipeline dài hạn nên set TTL lớn hơn thời gian chạy dự kiến
  • Debug — GET /debug/sessions, GET /api/v1/management/logs, Swagger UI tại /docs, Dashboard tại /dashboard
